# b_platform 需求规格说明书 V2.0

**项目：** b_platform（通用业务底座平台·控制面）  
**版本：** V2.0  
**状态：** 设计基线（待评审）  
**替代：** V1.3  
**数据库：** PostgreSQL 16+  
**技术基线：** Go / 模块化单体 / 扩展模块 SPI / 独立控制面

---

## 1. 引言

### 1.1 编写目的

本文档定义 b_platform V2.0 的产品定位、范围、功能需求、数据约束和非功能要求，作为架构设计、开发、测试、验收和后续扩展的依据。

V2.0 相比 V1.3 的核心变化：

1. Platform 从“根组织”改为**独立控制面**；
2. Tenant 与 Organization 解耦；
3. 核心只保留控制面能力，资源/预订/论坛移出核心；
4. 引入扩展模块 SPI；
5. 引入服务账号/API Key；
6. 技术栈改为 Go + PostgreSQL + 模块化单体；
7. 权限模型扩展为 Platform / Tenant / Organization 三层；
8. 明确不使用 `BYPASSRLS` 和自定义 GUC 做授权。

### 1.2 项目定位

b_platform 是一个独立开发、独立部署、独立演进的**业务基础平台**，为 Bufaa、Tufaa、MuPlan 及类似项目提供：

- 租户管理
- 身份认证
- 组织目录
- 成员关系
- 角色与权限
- 审计
- 平台配置
- 扩展模块注册
- 服务账号/API Key
- 事件出口

### 1.3 非目标

b_platform 不负责：

- 资源目录、资源发布
- 预订/预约
- 论坛
- 计费/结算
- 行业业务数据
- 文件/对象存储
- 邮件/短信/推送渠道实现（只定义接口/事件）
- 行业组织类型字典（由扩展或配置提供）

这些能力由扩展模块或独立业务系统实现。

## 2. 总体描述

### 2.1 系统角色

| 角色 | 说明 |
|---|---|
| 平台运营方 | 管理租户、平台角色、平台参数、扩展、服务账号 |
| 租户所有者 | 租户最高管理者，可转让 |
| 租户管理员 | 管理租户成员、角色、组织 |
| 租户审计员 | 查看租户审计 |
| 组织所有者 | 组织最高管理者，可转让 |
| 组织管理员 | 管理组织成员、角色 |
| 组织成员 | 组织内普通用户 |
| 普通用户 | 平台注册用户，可无租户归属 |
| 服务账号 | 供其他系统调用的机器身份 |
| 扩展模块 | 通过 SPI 接入的业务能力 |

### 2.2 三层模型

```text
Platform（控制面）
   │
   ├── Platform User / Platform Role / Platform Param
   │
   └── Tenant（数据隔离边界）
          │
          ├── Tenant Membership / Tenant Role
          │
          └── Organization（租户内业务组织，可树形）
                 │
                 ├── Organization Membership
                 └── Organization Role
```

### 2.3 运行环境

- 服务端：Go 1.23+，模块化单体。
- 数据库：PostgreSQL 16+。
- 部署：Docker Compose（一期），Kubernetes（后续）。
- API：REST / OpenAPI 3.1。
- 认证：JWT（RS256）+ Refresh Token；服务账号支持 Client Credentials / API Key。
- 多租户：共享库 + `tenant_id` + RLS 强制隔离。
- 扩展：编译期加载的 Go 模块，独立 schema。

### 2.4 设计约束

- Platform 不是 Organization，不进入组织树。
- Tenant 是数据隔离边界；Organization 属于 Tenant。
- 父子 Organization 必须同 Tenant。
- 所有租户数据表必须含 `tenant_id` 并启用 RLS。
- 运行时数据库角色不得拥有 `BYPASSRLS`。
- 不使用 `app.is_platform_access`、`app.is_platform_write` 等 GUC 做授权。
- 所有主键使用 UUIDv7，禁止自增 ID。
- 权限点编码一经发布不可修改，只能废弃后新增。
- 核心不硬编码资源/预订/论坛等业务域。
- 扩展模块不得直接访问核心表。

## 3. 功能需求

### 3.1 租户管理（FR-T）

**FR-T-01 创建租户**  
平台运营方可以创建租户，指定名称、标识、初始所有者。创建租户时在同一事务内创建初始租户所有者成员关系和角色。

**FR-T-02 租户查询**  
平台运营方可以查询租户列表和详情；租户成员可以查看自己所属租户。

**FR-T-03 租户更新**  
租户管理员可以更新租户名称、配置；租户标识不可修改。

**FR-T-04 租户冻结/解冻**  
平台运营方可以冻结/解冻租户。冻结期间拒绝该租户下所有业务写操作；平台仅允许解冻或经审计的强制管理。

**FR-T-05 租户关闭**  
一期不提供物理删除；关闭仅置状态并保留数据。关闭后禁止登录和写入。

**FR-T-06 租户隔离**  
任一租户成员不得通过接口、错误 ID、关联查询或伪造上下文访问其他租户数据。

### 3.2 身份与认证（FR-I）

**FR-I-01 用户注册**  
支持邮箱/手机号注册，注册后须完成联系方式验证。账号全局唯一。

**FR-I-02 登录**  
支持账号密码登录，签发 Access Token + Refresh Token。平台入口与普通用户入口使用不同 `aud`。

**FR-I-03 刷新令牌**  
Refresh Token 旋转；检测重用；密码重置/禁用后失效。

**FR-I-04 登出**  
登出使当前 Refresh Token 失效。

**FR-I-05 密码重置**  
支持忘记密码、一次性重置令牌、重置后所有会话失效。

**FR-I-06 联系方式验证**  
支持邮箱/手机验证令牌，一次性、有时效。

**FR-I-07 登录失败限制**  
连续失败达到阈值后锁定一段时间；支持按账号/IP 限流。

**FR-I-08 用户禁用/启用**  
平台运营方可以禁用/启用用户。禁用后所有会话失效；重新启用不自动恢复租户成员关系。

**FR-I-09 会话管理**  
用户可以查看/撤销自己的会话；平台管理员可以撤销指定用户会话。

**FR-I-10 多租户切换**  
用户可以在自己有有效成员关系的租户/组织之间切换；切换后重新签发上下文 Token。

**FR-I-11 服务账号认证**  
服务账号支持 OAuth2 Client Credentials 和 API Key；API Key 只存哈希，支持过期/撤销。

### 3.3 组织管理（FR-O）

**FR-O-01 创建组织**  
租户内有权限的成员可以创建组织；组织必须属于当前租户。

**FR-O-02 组织审批**  
组织创建可配置为需要审批；审批在租户内完成；审批通过后创建者成为组织所有者。

**FR-O-03 组织树**  
组织支持父子层级；父子必须同租户；深度受租户/平台参数限制。

**FR-O-04 组织查询**  
租户成员可以按权限查看组织及其下级；不得跨租户。

**FR-O-05 组织更新**  
组织管理员可以更新组织名称、配置、可见性策略。

**FR-O-06 组织冻结/解冻**  
租户管理员或平台运营方可以冻结/解冻组织；冻结期间拒绝该组织写操作；祖先冻结时可级联拒绝（可配置）。

**FR-O-07 组织所有者转让**  
组织所有者可以发起转让；目标必须是有效组织成员；支持平台强制转让（需审计）。

**FR-O-08 组织删除/迁移**  
一期不支持组织物理删除和父组织变更；接口明确拒绝。

### 3.4 成员与角色（FR-M）

**FR-M-01 租户成员**  
租户管理员可以邀请/移除租户成员；成员可拥有多个租户角色。

**FR-M-02 组织成员**  
组织管理员可以邀请/移除组织成员；组织成员必须是租户成员。

**FR-M-03 成员状态**  
成员状态包括 `INVITED`、`ACTIVE`、`SUSPENDED`、`INACTIVE`；移除保留历史记录。

**FR-M-04 角色管理**  
租户/组织可以创建自定义角色，角色权限点集合必须是操作者权限集合的子集。

**FR-M-05 角色分配**  
支持一个成员多个角色；角色停用/移除后下一请求即时失效。

**FR-M-06 提权防护**  
授予/修改角色时，目标权限集合必须 ⊆ 操作者权限集合；超级管理员授予统一使用 `platform.role.grant`（不设专用权限点，见权限模型 §8.4）。

**FR-M-07 所有者保护**  
租户/组织所有者角色受硬保护，只能通过专用转让流程变更；任一租户/组织任一时刻只有一个所有者。

**FR-M-08 平台角色授予**  
平台角色支持授权范围：`ALL`、`TENANT`、`ORGANIZATION`、`ORG_TYPE`；多范围并集；默认不含下级，可选包含后代。

**FR-M-09 权限即时生效**  
成员移除、角色变更、用户禁用等操作递增权限版本；旧 Token/缓存不得继续使用。

### 3.5 权限点（FR-P）

**FR-P-01 权限点注册**  
核心权限点由平台维护；扩展权限点由扩展 Manifest 注册，命名空间为 `ext.<module>.*`。

**FR-P-02 权限点作用域**  
权限点作用域为 `PLATFORM`、`TENANT`、`ORGANIZATION`。

**FR-P-03 权限点不可变**  
编码发布后不可修改；只能废弃后新增。

**FR-P-04 统一判定**  
所有授权判定统一走 `authz.Authorizer`；禁止在 Handler/Service 中硬编码角色判断。

**FR-P-05 扩展权限**  
扩展只能注册 `TENANT`/`ORGANIZATION` 作用域权限；不能注册 `PLATFORM` 权限。

### 3.6 审计（FR-A）

**FR-A-01 审计事件**  
覆盖登录、注册、密码重置、用户禁用、租户创建/冻结、组织创建/审批/冻结、成员邀请/移除、角色变更、所有者转让、平台角色授予、服务账号/API Key 变更、扩展启用/禁用、跨租户访问。

**FR-A-02 同事务写入**  
关键安全事件与业务事务同事务写入；审计失败则业务失败并回滚。

**FR-A-03 只追加**  
审计记录不更新、不删除；应用角色仅插入。

**FR-A-04 审计查询**  
租户审计员查看本租户审计；平台审计员查看全平台审计；审计查询本身记录审计。

**FR-A-05 审计归档**  
支持按时间分区、导出 SIEM/对象存储；保留周期可配置。

### 3.7 平台配置（FR-C）

**FR-C-01 平台参数**  
平台运营方可以管理平台参数（如登录失败阈值、Token TTL、组织树深度上限、是否允许组织审批）。

**FR-C-02 租户配置**  
租户管理员可以管理租户级配置；配置使用 JSON Schema 校验；变更审计。

**FR-C-03 配置可见性**  
平台参数区分公开/平台私有；租户只能读取公开参数。

### 3.8 扩展模块（FR-E）

**FR-E-01 扩展注册**  
扩展通过 Manifest 注册名称、版本、API 版本、权限、路由、迁移、事件、配置 schema、UI 扩展点。

**FR-E-02 扩展启用/禁用**  
平台运营方可以启用/禁用扩展；禁用不删除数据；路由不挂载。

**FR-E-03 扩展隔离**  
扩展使用独立 schema `ext_<module>`；不得修改核心表；不得直接访问核心表。

**FR-E-04 扩展权限**  
扩展权限注册到 `permission` 表（`namespace='EXT'`，`module=<module>`）；平台/租户/组织角色可以授予。

**FR-E-05 扩展升级**  
扩展升级必须兼容当前 API 版本；迁移独立管理。

### 3.9 服务账号与 API Key（FR-S）

**FR-S-01 创建服务账号**  
平台运营方/租户管理员可以创建服务账号，指定名称、作用域、有效期。

**FR-S-02 Client Credentials**  
服务账号可使用 OAuth2 Client Credentials 获取 Token；Token 包含 `aud=service` 和 scopes。

**FR-S-03 API Key**  
服务账号可以创建 API Key；API Key 只存哈希，显示一次；支持过期/撤销。

**FR-S-04 审计**  
服务账号创建、密钥轮换、撤销、使用异常均审计。

### 3.10 事件与集成（FR-X）

**FR-X-01 Outbox**  
关键领域事件与业务同事务写入 Outbox；Worker 异步投递。

**FR-X-02 Webhook**  
支持租户配置 Webhook 端点；HMAC 签名；重试、死信、延迟告警。

**FR-X-03 JWT/JWKS**  
对外提供 JWKS 端点；其他项目可本地校验 JWT。

**FR-X-04 OpenAPI**  
核心 API 提供 OpenAPI 3.1 契约；扩展 API 合并到契约。

**FR-X-05 契约测试**  
核心与扩展、核心与消费方之间建立契约测试。

## 4. 数据需求

### 4.1 核心实体

| 实体 | 关键属性 | 约束 |
|---|---|---|
| Platform User | ID、账号、状态、密码哈希、权限版本 | 账号全局唯一；不参与租户 RLS |
| Tenant | ID、标识、名称、状态、所有者、配置 | 标识唯一；平台控制面创建 |
| Tenant Membership | 租户 ID、用户 ID、状态、权限版本 | 同一用户同一租户有效记录唯一 |
| Organization | ID、租户 ID、父 ID、类型、名称、状态、所有者 | 父子同租户；树深度受限 |
| Organization Closure | 租户 ID、祖先 ID、后代 ID、深度 | `(tenant_id, ancestor, descendant)` 唯一 |
| Organization Membership | 租户 ID、组织 ID、用户 ID、状态、权限版本 | 同用户同组织有效记录唯一；必须是租户成员 |
| Role | ID、作用域、租户 ID、组织 ID、名称、类型 | 作用域与租户/组织字段一致；所有者角色唯一 |
| Permission | 编码、命名空间、作用域、状态、是否扩展 | 编码全局唯一且不可改 |
| Role Permission | 角色 ID、权限编码 | 联合唯一 |
| Platform Role Grant | 用户 ID、平台角色 ID、状态 | `(用户, 角色)` 有效授予唯一 |
| Platform Role Grant Scope | 授予 ID、范围类型、租户/组织/类型、是否含下级 | 范围类型与字段一致 |
| Audit Log | 租户 ID、操作者、目标、动作、结果、IP、快照 | 只追加；租户 RLS；平台审计独立 |
| Service Account | ID、租户 ID、名称、client_id、secret 哈希、状态 | 租户/平台作用域 |
| API Key | ID、租户 ID、服务账号 ID、key 哈希、前缀、状态 | 只存哈希 |
| Extension Registry | 名称、版本、API 版本、状态、Manifest | 名称唯一 |
| Outbox Event | 租户 ID、聚合、事件类型、payload、状态 | 与业务同事务 |
| Idempotency Key | 租户 ID、主体、端点、键、请求哈希、响应 | 联合唯一 |

### 4.2 数据隔离

- 所有租户表含 `tenant_id`，启用 RLS。
- 策略默认拒绝：`tenant_id = current_setting('app.tenant_id', true)::uuid`。
- 平台级表不启用租户 RLS，但通过数据库角色和表级授权限制。
- 平台跨租户访问：`platform_control` 设置目标 `app.tenant_id`，同一事务写审计。
- 不使用 `BYPASSRLS`。
- 不使用自定义 GUC 表示平台身份/写权限。
- 连接池复用、回滚、异常、后台任务必须正确设置/清除租户上下文。

### 4.3 数据保留

- 租户关闭不删除数据。
- 用户禁用不删除成员关系，仅置失效。
- 成员重新加入创建新记录，保留历史。
- 角色、权限点、扩展采用停用/废弃，不物理删除。
- 审计保留周期可配置，默认不少于 180 天。

## 5. 非功能需求

### 5.1 安全性

- 密码使用 Argon2id。
- JWT 使用 RS256；支持密钥轮换/JWKS。
- 平台管理员敏感操作支持 MFA/step-up（二期）。
- 登录、注册、密码重置、API Key 使用限流。
- 所有权限判定在服务端执行。
- 所有租户表 RLS + 数据库角色最小权限。
- 关键审计同事务；审计不可更新/删除。
- 定期渗透测试，覆盖 IDOR、租户逃逸、权限提升、SQL 注入。
- 密钥通过环境变量/KMS/Secret Manager 注入，不写入代码库。

### 5.2 可扩展性

- 核心不硬编码业务域。
- 扩展通过 SPI 注册。
- 权限点命名空间可扩展，不修改核心表结构。
- 租户配置/平台参数支持 JSON Schema。
- 数据隔离支持共享库 RLS；后续可扩展 schema-per-tenant/database-per-tenant。

### 5.3 性能

- 认证/授权 P95 ≤ 50ms（不含网络）。
- 组织树查询 P95 ≤ 300ms（单租户万级组织）。
- 租户列表/成员列表分页响应 P95 ≤ 500ms。
- 支持 10,000+ 租户、1,000,000+ 用户。
- RLS 关键表建立 `tenant_id` 索引。
- 审计表按时间分区。

### 5.4 可靠性

- 关键操作幂等。
- 关键审计同事务。
- Outbox 至少一次投递，消费者幂等。
- 数据库备份 + PITR；RPO ≤ 15 分钟，RTO ≤ 1 小时（生产）。
- 迁移可重复执行/可回滚；生产采用 expand/contract。
- 平台 API 多实例无状态；优雅关闭。

### 5.5 可维护性

- 模块边界清晰，禁止跨模块表访问。
- 所有 SQL 经 `sqlc` 生成；复杂 SQL 审查。
- OpenAPI 契约先行。
- ADR 记录关键决策。
- 迁移、RLS、授权、审计测试纳入 CI。
- 代码规范：`golangci-lint`、`staticcheck`、`govulncheck`。

## 6. 验收标准

1. 平台运营方可以创建租户，并自动创建租户所有者成员关系和角色。
2. 用户注册、登录、刷新、登出、密码重置、联系方式验证闭环可用。
3. 用户可以在多个租户/组织之间切换，Token 中的租户/组织上下文正确。
4. 租户管理员可以邀请成员、分配多个租户角色；组织管理员可以管理组织成员和角色。
5. 组织支持树形结构，父子同租户，深度受参数限制；跨租户父子被拒绝。
6. 组织审批、冻结、所有者转让状态机完整，重复请求幂等。
7. 提权防护生效：不能授予自身没有的权限；不能操作所有者角色。
8. 平台角色支持 `ALL`、`TENANT`、`ORGANIZATION`、`ORG_TYPE` 授权范围；多范围并集；含下级可选。
9. 任一租户成员无法通过接口、错误 ID、关联查询获取其他租户数据；RLS 测试通过。
10. 运行时数据库角色无 `BYPASSRLS`；不能通过 GUC 伪造平台访问。
11. 审计覆盖关键事件；关键审计与业务同事务；应用角色不能更新/删除审计。
12. 扩展模块可以注册权限、路由、迁移、事件、配置；禁用扩展不影响核心。
13. 服务账号可以通过 Client Credentials/API Key 调用授权范围内的 API。
14. OpenAPI 契约与实现一致；错误响应、分页、幂等符合契约。
15. 性能验收达到目标；备份恢复演练通过。
16. 安全测试覆盖租户逃逸、IDOR、权限提升、SQL 注入、Token 重放。
